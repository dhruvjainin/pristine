# Pattern: chat and agent surfaces

Use whenever the target has a message composer, streaming responses, or agent/tool activity. The goal is a conversation the Persona can trust: what they type is never lost, every reply and tool step shows what really happened, and nothing sends twice.

## Placement and journeys

- **The requested surface is part of the task.** Before editing, record the discovery route, execution route and region selector for each stage: offer, inputs, approvals, progress and result. If execution belongs in a conversation, use the actual conversation with its saved identity and composer, not a separate page styled like chat. Reuse its existing canvas or side-panel contract: "in chat" does not mean every component belongs inline. Resolve unspecified placement before building it.
- **Prove placement and the complete journey.** Start at the discovery route and follow the real controls. Verify the requested design-system component by its actual import, not a similar appearance. Query that component inside its assigned region, with zero duplicate full views in other regions unless explicitly requested. For a plan or progress view that lives in a side canvas, require one full view inside the canvas and zero in the transcript, and exercise the mobile panel. Require zero unrequested route changes during execution. Reload and verify the same server operation ID and status; navigation and reload create zero new execution requests or review decisions. Completion must agree with the real operation response, not a timed animation or seeded success.
- **A plan's hierarchy needs real data.** When the brief shows grouped work, populate the component's child structure; the right component with a flat array is not equivalent. Each group exposes its child tasks and a short description, and its done/total count equals its actual descendant leaves. Overall progress counts each execution leaf once, not group headers. Flattening the display tree preserves the ordered task IDs and dependencies exactly. Before an execution order exists, label the view as a preview. Keep any required verification as the last leaf and never show success before its real result.
- **Task names describe work, not storage keys.** Primary task labels use supplied display names and a clear action, not raw `kind: key` or UUID labels. Keep identifiers and dependencies in expanded details. Do not invent owners or descriptions absent from the source. Counts do not change on expand/collapse.
- **Simplified labels keep the item's type.** A plan mixing resource types keeps a visible type cue on every leaf, even when collapsed; a clock, spinner or check is status, not type. Reuse the exact type icons from the product's navigation, with type text in each row's accessible name or description. The type cue stays while status changes. Follow the icon checks in [consistency](../lenses/consistency.md).

## Composer

- **Controls match what the backend can run.** With a restricted backend fixture, every composer instance shows the effective model, tool, or other limited option and offers zero unsupported selections. An unsupported stored preference is corrected before a new send is enabled: the visible label and the outgoing request field agree with what the backend actually runs. Replaying an existing request preserves its original payload and request ID.
- **A handoff keeps the live input.** When a composer moves to another view in the same document (e.g. home page → conversation), save the input/editor DOM node, draft and selection before navigation. After handoff the node is strictly equal (`===`), still connected, and keeps its draft and selection. A late effect that remounts the editor fails. A deliberate send produces exactly one send request; navigation, reload and Back/Forward produce zero.
- **Bot verification gates sending, not drafting.** While a background check runs, every composer stays editable and shows zero challenge panel or reserved height; all submit paths (button, Enter) stay blocked until the server has verified the session. A client token alone never unlocks Send. Verification transitions (silent → interactive → retry → verified) keep editor identity, draft, selection and focus, and create zero sends. Announce why a draft can't send yet in a status region. Errors and expiry never unlock Send.

## Replies and progress

- **One reply, one progress presentation.** Reuse the design system's thinking or activity component. Before the first response text, each pending reply has one thinking indicator or a live tool-activity region, not both. Parallel tools may each show their own state within that region. On completion, cancellation or failure, no active progress remains.
- **Tool work is visible and factual.** Render each authorized tool event's label and state before the answer arrives. A running tool has zero additional generic thinking indicators. Replaying the same event adds zero rows; stale attempts cannot change its state. After reload, the same saved tool events stay inspectable in their persisted order. Never invent calls or reconstruct redacted URLs and arguments.
- **Finished steps yield to live work.** When preflight tool calls finish and live work (sub-agents, results, an approval) appears below, the finished list folds to one header row ("Used 3 tools") that reopens by click and by Enter/Space. Running steps and failures stay open. A finished list never pushes the live work below the fold.
- **Live labels are readable on arrival.** Sample each frame from insertion through completion for running and completed tool/status labels in both themes. Composite text and ancestor opacity against the actual background; small text keeps ≥ 4.5:1 from its first visible frame. If a component fades a label through low contrast, remove only that label's fade and keep unrelated spinner motion.
- **Summaries name each entity once.** A summary of repeated tool actions (one badge per provider) deduplicates in first-seen order, with zero duplicate-key warnings. Keep every distinct action row; never deduplicate the rows themselves or hide the warning with index keys.
- **Empty history is not a new conversation.** The first-run welcome is absent while sending, loading an existing conversation, restoring an interrupted send, streaming or recovering from an error. An empty existing conversation has its own empty state. A load failure never replaces retained messages with the welcome screen.
- **Streaming is observed before completion.** The first chunk renders while later chunks and the terminal event are withheld; the second chunk extends the same reply. Revealing a completed answer with timers does not pass.
- **Recovery preserves identity and text.** After a dropped and reconnected stream plus a replayed event, shown text remains, replay adds no duplicate text, and history ends with exactly one final reply. Reconnecting alone creates zero sends. Switching conversations closes the old subscription and cannot leak its partial reply.

## First render and reload

- **First-render parity includes restored browser state.** Server HTML and the first client render have the same element structure on direct entry and on reload after a same-document handoff. `history.state` survives reload; `typeof window !== "undefined"` only prevents a server error, not a hydration mismatch. Initialize from server-known route state; consume a handoff marker only after observing the source → destination transition in the mounted document.

## Verify

In each Capture Matrix cell:

- **Lifecycle:** capture the first-send wait, tool running/completed/failed states, first text chunk, growing reply, completed reply, and interrupted/error state. Also exercise restored sends, delayed history, reloaded tool events, stream reconnection and conversation switching. Hold chunks and completion at the transport, not with a visual typing timer. Label synthetic transport evidence separately from a real provider run; a final-response fixture does not verify streaming or tool visibility.
- **Entry paths:** direct load, direct reload, source → destination handoff, reload on that same history entry (keep the marker; a fresh browser context misses it), and Back/Forward. Keep console listeners on throughout: zero hydration warnings or errors, the standalone layout after reload, editor node identity on the live handoff, and zero navigation-triggered sends. Repeat with application API calls blocked so an API failure can't hide a hydration fault.
- **Verification:** capture silent, human-required, error/retry and verified states; hold the server response after a token arrives and confirm Send stays disabled.
- **Placement:** capture the old failure and the corrected journey; a different component or a working view in the wrong region does not pass.
- Record request counts for every check that asserts "zero sends" or "exactly one send".
